# ارتقای رابط مشترک Flavor

شروع: ۲ اکتبر ۲۰۲۶. مبنا: `edd08b1`. هویت و ترکیب صفحهٔ اصلی ۱۲ دمو حفظ می‌شود؛ منطق سفارش، مبلغ و پرداخت همچنان در Flavor Core و ووکامرس است.

| مرحله | دامنه | وضعیت |
|---|---|---|

## قرارداد طراحی و ایمنی

- پالت، فونت و شخصیت هر پوسته به ارث می‌رسد؛ رنگ متن دکمه و متن فرعی برای خوانایی محاسبه می‌شود.
- اطلاعات محصول، قیمت، انتخاب‌ها، ظرفیت رزرو و وضعیت سفارش باید از دادهٔ واقعی خوانده شوند، نه تایم‌لاین یا امتیاز نمایشی.
- دیدن محصول، انتخاب شعبه و بازکردن پنل نباید خودکار غذا یا سفارش بسازد.
- رابط در عرض‌های ۳۲۰ تا ۱۴۴۰، با کیبورد، کاهش حرکت و حالت بدون JavaScript بررسی می‌شود.
- در تست‌ها پرداخت، پیامک واقعی و سفارش مشتری انجام نمی‌شود. تست‌های مخرب تنها با رضایت صریح `FLAVOR_DEMO_QA=1` روی وردپرس دورریختنی مجازند.
- توکن GitHub در فایل‌ها یا تنظیمات مخزن ذخیره نمی‌شود.

## آزمون‌ها

نتایج هر مرحله و دستورهای قابل تکرار در ادامهٔ همین سند تکمیل می‌شود. آزمون‌های دمو در `tests/demos` و آزمون‌های رابط مشترک در `tests/ui` قرار دارند.

### مرحلهٔ ۱ — نتیجه

منوی کارتی/فهرستی، دسته‌بندی چسبان با تعداد واقعی، جزئیات تصویری غذا، انتخاب‌های گروه‌بندی‌شده، قیمت نهایی و تعداد، راهنمای حساسیت غذایی، بازگشت فوکوس/فوکوس محدود و لینک محصول بدون افزودن خودکار تکمیل شدند. منوی بدون JavaScript واقعاً از ووکامرس رندر می‌شود. انتخاب نتیجهٔ جست‌وجو به جزئیات همان غذا در منو می‌رود.

آزمون واقعی وردپرس: پنج عرض ۳۲۰/۳۹۰/۷۶۸/۱۰۲۴/۱۴۴۰، منوی دسکتاپ/موبایل و پنل محصول بدون خطای خودکار WCAG، فیلتر/نمایش، Escape و بازگشت فوکوس، مبلغ تعداد، لینک محصول و سبد ماندگار عبور کردند. رنگ کنترل‌ها در هر ۱۲ پوسته بررسی شد.

```bash
php tests/ui/tokens.php
cd tests/ui && npm ci
npx playwright install --with-deps chromium
SITE_URL=https://your-disposable-wordpress.example/ UI_STAGE=1 npm test
```

### مرحلهٔ ۲ — نتیجه

سبد تصویری با ویرایش تعداد و حذف صریح، دو گام مرور/دریافت و اطلاعات/پرداخت، مبلغ‌های واقعی سرور، تخفیف/مالیات/کارمزد، هزینهٔ جداگانهٔ محدوده، حالت خالی و حفظ سبد/فیلدها در خطای پرداخت تکمیل شد. حالت‌های دریافت و پرداخت فقط از تنظیمات واقعی شعبه می‌آیند. واکنش ویرایش سبد اعلام می‌شود و کنترل‌های کیبورد/فوکوس در دراور حفظ می‌شوند. فرم‌های اصلی ووکامرس نیز بدون جایگزین‌کردن قالب درگاه یا اعتبارسنجی آن سبک مشترک گرفتند.

برای هماهنگی واحد قیمت هر ردیف، فیلدهای عددی و HTML **اختیاری و افزایشی** به پاسخ سبد اضافه شد؛ کلیدهای قدیمی و مسیرهای API حفظ شده‌اند. جمع فعلی سبد از سرور است؛ مبلغ ارسال بررسی‌شده، تا وقتی در جمع سرور منظور نشده، به‌عنوان هزینهٔ جداگانه نمایش داده می‌شود و جمع نهایی ساختگی نیست.

آزمون افزودنی واقعی یک ایراد قدیمی را آشکار کرد: هر بار محاسبهٔ ووکامرس مبلغ افزودنی دوباره روی قیمتِ تغییرکرده جمع می‌شد. مبنای محاسبه اکنون قیمت تازهٔ کاتالوگ است؛ قاعده همان «قیمت پایه + افزودنی انتخاب‌شده» است، نه یک قاعدهٔ مالی جدید. چهار محاسبهٔ پیاپی و تعداد دو در آزمون وردپرس مبلغ ثابت و صحیح دادند.

مرورگر: ویرایش/حذف واقعی، تطبیق مبلغ ردیف با سرور، سبد/تسویهٔ دسکتاپ و موبایل، محدودهٔ زنده، خطای پرداخت **رهگیری و جایگزین‌شده در خود مرورگر، بدون ایجاد سفارش**، حفظ سبد و امکان تلاش مجدد، حالت خالی و WCAG خودکار عبور کردند. آزمون pure Core: ۱۵/۱۵؛ mock قدیمی: همچنان ۷۴/۷۹ با همان پنج شکست رزرو.

```bash
FLAVOR_DEMO_QA=1 wp eval-file /path/to/repo/tests/ui/cart.php
cd tests/ui
SITE_URL=https://your-disposable-wordpress.example/ UI_STAGE=2 npm test
```
