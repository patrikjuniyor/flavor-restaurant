# ارتقای رابط مشترک Flavor

شروع: ۲ اکتبر ۲۰۲۶. مبنا: `edd08b1`. هویت و ترکیب صفحهٔ اصلی ۱۲ دمو حفظ می‌شود؛ منطق سفارش، مبلغ و پرداخت همچنان در Flavor Core و ووکامرس است.

## قرارداد طراحی و ایمنی

- پالت، فونت و شخصیت هر پوسته به ارث می‌رسد؛ رنگ متن دکمه و متن فرعی برای خوانایی محاسبه می‌شود.
- اطلاعات محصول، قیمت، انتخاب‌ها، ظرفیت رزرو و وضعیت سفارش باید از دادهٔ واقعی خوانده شوند، نه تایم‌لاین یا امتیاز نمایشی.
- دیدن محصول، انتخاب شعبه و بازکردن پنل نباید خودکار غذا یا سفارش بسازد.
- رابط در عرض‌های ۳۲۰ تا ۱۴۴۰، با کیبورد، کاهش حرکت و حالت بدون JavaScript بررسی می‌شود.
- در تست‌ها پرداخت، پیامک واقعی و سفارش مشتری انجام نمی‌شود. تست‌های مخرب تنها با رضایت صریح `FLAVOR_DEMO_QA=1` روی وردپرس دورریختنی مجازند.
- توکن GitHub در فایل‌ها یا تنظیمات مخزن ذخیره نمی‌شود.

## آزمون‌ها

نتایج هر مرحله و دستورهای قابل تکرار در ادامهٔ همین سند تکمیل می‌شود. آزمون‌های دمو در `tests/demos` و آزمون‌های رابط مشترک در `tests/ui` قرار دارند.

### مرحلهٔ ۱ — نتیجه

منوی کارتی/فهرستی، دسته‌بندی چسبان با تعداد واقعی، جزئیات تصویری غذا، انتخاب‌های گروه‌بندی‌شده، قیمت نهایی و تعداد، راهنمای حساسیت غذایی، بازگشت فوکوس/فوکوس محدود و لینک محصول بدون افزودن خودکار تکمیل شدند. منوی بدون JavaScript واقعاً از ووکامرس رندر می‌شود. انتخاب نتیجهٔ جست‌وجو به جزئیات همان غذا در منو می‌رود.

آزمون واقعی وردپرس: پنج عرض ۳۲۰/۳۹۰/۷۶۸/۱۰۲۴/۱۴۴۰، منوی دسکتاپ/موبایل و پنل محصول بدون خطای خودکار WCAG، فیلتر/نمایش، Escape و بازگشت فوکوس، مبلغ تعداد، لینک محصول و سبد ماندگار عبور کردند. رنگ کنترل‌ها در هر ۱۲ پوسته بررسی شد.

```bash
php tests/ui/tokens.php
cd tests/ui && npm ci
npx playwright install --with-deps chromium
SITE_URL=https://your-disposable-wordpress.example/ UI_STAGE=1 npm test
```

### مرحلهٔ ۲ — نتیجه

سبد تصویری با ویرایش تعداد و حذف صریح، دو گام مرور/دریافت و اطلاعات/پرداخت، مبلغ‌های واقعی سرور، تخفیف/مالیات/کارمزد، هزینهٔ جداگانهٔ محدوده، حالت خالی و حفظ سبد/فیلدها در خطای پرداخت تکمیل شد. حالت‌های دریافت و پرداخت فقط از تنظیمات واقعی شعبه می‌آیند. واکنش ویرایش سبد اعلام می‌شود و کنترل‌های کیبورد/فوکوس در دراور حفظ می‌شوند. فرم‌های اصلی ووکامرس نیز بدون جایگزین‌کردن قالب درگاه یا اعتبارسنجی آن سبک مشترک گرفتند.

برای هماهنگی واحد قیمت هر ردیف، فیلدهای عددی و HTML **اختیاری و افزایشی** به پاسخ سبد اضافه شد؛ کلیدهای قدیمی و مسیرهای API حفظ شده‌اند. جمع فعلی سبد از سرور است؛ مبلغ ارسال بررسی‌شده، تا وقتی در جمع سرور منظور نشده، به‌عنوان هزینهٔ جداگانه نمایش داده می‌شود و جمع نهایی ساختگی نیست.

آزمون افزودنی واقعی یک ایراد قدیمی را آشکار کرد: هر بار محاسبهٔ ووکامرس مبلغ افزودنی دوباره روی قیمتِ تغییرکرده جمع می‌شد. مبنای محاسبه اکنون قیمت تازهٔ کاتالوگ است؛ قاعده همان «قیمت پایه + افزودنی انتخاب‌شده» است، نه یک قاعدهٔ مالی جدید. چهار محاسبهٔ پیاپی و تعداد دو در آزمون وردپرس مبلغ ثابت و صحیح دادند.

مرورگر: ویرایش/حذف واقعی، تطبیق مبلغ ردیف با سرور، سبد/تسویهٔ دسکتاپ و موبایل، محدودهٔ زنده، خطای پرداخت **رهگیری و جایگزین‌شده در خود مرورگر، بدون ایجاد سفارش**، حفظ سبد و امکان تلاش مجدد، حالت خالی و WCAG خودکار عبور کردند. آزمون pure Core: ۱۵/۱۵؛ mock قدیمی: همچنان ۷۴/۷۹ با همان پنج شکست رزرو.

```bash
FLAVOR_DEMO_QA=1 wp eval-file /path/to/repo/tests/ui/cart.php
cd tests/ui
SITE_URL=https://your-disposable-wordpress.example/ UI_STAGE=2 npm test
```

### مرحلهٔ ۳ — نتیجه

نوار موبایل مشترک جایگزین دو پیاده‌سازی قبلی شد؛ حساب/تماس/رزرو بر اساس صفحه و امکانات واقعی نمایش داده می‌شوند. کترینگ مسیر هماهنگی خود را حفظ می‌کند. سبد از صفحهٔ دیگر با `open_cart=1` مستقیماً باز می‌شود و شمارندهٔ موبایل از سبد واقعی خوانده می‌شود. بدون JavaScript لینک سبد به ووکامرس می‌رود.

منوی موبایل همهٔ پوسته‌ها فوکوس محدود، Escape، بازگشت فوکوس، inert و بستن هنگام تغییر عرض دارد. پیام‌های کوتاه قابل‌خواندن و کاهش حرکت پشتیبانی می‌شوند. شاخهٔ منتشرنشده، توکن QR نامعتبر و سرویس بدون سالن، میز یا رزرو جعلی معرفی نمی‌کنند. جدول فعالِ متعلق به شعبه در سرصفحه نمایان و در فرم دریافت پیش‌انتخاب می‌شود.

آزمون مرورگر رابط و بازبینی دموی پک عبور کردند؛ آزمون محلی QR، میز/توکن صحیح، توکن نامعتبر، بیرون‌بر بدون سالن و شعبهٔ پیش‌نویس را بررسی کرد.

```bash
FLAVOR_DEMO_QA=1 wp eval-file /path/to/repo/tests/ui/context.php
cd tests/ui
SITE_URL=https://your-disposable-wordpress.example/ UI_STAGE=3 npm test
```

### مرحلهٔ ۴ — نتیجه

ورود پیامکی روی API موجود Core با درخواست/تأیید صریح، خطای شماره و کد، توقف ارسال دوباره و نشست HttpOnly ووکامرس پیاده شد. پذیرش درخواست به معنی تحویل تضمینی پیامک معرفی نمی‌شود. توکن Bearer/refresh، رمز یا کد پیگیری در local/session storage یا URL ذخیره نمی‌شوند؛ حساب با کوکی موجود Core کار می‌کند. ورود با رمز عبور و فرم‌های اصلی ووکامرس محفوظ‌اند.

پیشخوان مشتری، شمار واقعی سفارش‌ها/امتیازها/مهرها، سفارش‌های اخیر، تاریخچه و رسید اصلی سبک یکپارچه دارند. اطلاعات فقط برای صاحب حساب، مدیر مجاز یا رسید با کلید معتبر نمایش داده می‌شوند. کد پیگیری مهمان در رسید مجاز ماسک شده و کپی/نمایش آن صریح است.

پیگیری جدید، شناسه و کد خصوصی را در هدر درخواست می‌فرستد؛ رد دسترسی، نتیجهٔ قبلی را پاک می‌کند. مراحل آشپزخانه تنها در صورت وجود رکورد واقعی نمایش داده می‌شوند؛ تخمین ثابت یا تحویل به پیک از وضعیت «آماده» جعل نمی‌شود. پاسخ جزئیات سفارش یک فلگ افزایشی برای وجود رکورد آشپزخانه دارد و تبدیل مبلغ، واحد ثبت‌شدهٔ خود سفارش را می‌خواند، نه واحد فعلی فروشگاه.

آزمون: درخواست SMS در مرورگر رهگیری شد، اما تأیید کد از هش Fixture و نشست واقعی Core عبور کرد؛ هیچ پیامک واقعی ارسال نشد. حساب/تاریخچه/رسید، رد سفارش مشتری دیگر، پیگیری صحیح مهمان و رد کد نادرست، عدم نگه‌داشتن نتیجهٔ خصوصی بعد از خطا و دسترس‌پذیری دسکتاپ/موبایل عبور کردند. سفارش‌های این آزمون، Fixture مشخص‌شده در وردپرس دورریختنی‌اند، نه سفارش مشتری یا پرداخت واقعی.

```bash
FLAVOR_DEMO_QA=1 wp eval-file /path/to/repo/tests/ui/fixtures.php
FLAVOR_DEMO_QA=1 wp eval-file /path/to/repo/tests/ui/customer.php
cd tests/ui
SITE_URL=https://your-disposable-wordpress.example/ UI_STAGE=4 npm test
# پاک‌کردن فقط Fixtureهای مشخص‌شده:
UI_QA_CLEANUP=1 FLAVOR_DEMO_QA=1 wp eval-file /path/to/repo/tests/ui/fixtures.php
```

### مرحلهٔ ۵ — نتیجه

صفحات درباره/تماس، فهرست و جزئیات شعبه، رزرو، ۴۰۴ و جست‌وجوی بدون JavaScript بازطراحی شدند. فیلتر نام/شهر شعبه، شمارهٔ تماس فارسی با لینک تلفنی معتبر، ساعات فقط از تنظیمات ثبت‌شده و لینک نقشه فقط با مختصات معتبر ساخته می‌شوند؛ «همیشه باز» یا موقعیت فرضی نمایش داده نمی‌شود. محتوای سفارشی و قالب‌های انتخاب‌شدهٔ کاربر حفظ می‌شوند؛ صفحات سازنده/المنتور جایگزین نمی‌شوند.

رزرو سه بخش روشن دارد: شعبه/مهمان، تقویم/ظرفیت و اطلاعات هماهنگی. فقط شعبه‌های دارای سالن و میز فعال و بخش‌های واقعی همان میزها معرفی می‌شوند. انتخاب روز/ساعت برای صفحه‌خوان نام‌گذاری شده، درخواست‌های قدیمی تقویم/ظرفیت کنار گذاشته می‌شوند و بدون JavaScript مسیر تماس ارائه می‌شود. صفحهٔ ۴۰۴ همان HTTP 404 را حفظ می‌کند.

در آزمون انتخاب شعبه، برخورد نام پارامتر عددی `flavor_branch` با query-var پست‌تایپ وردپرس آشکار شد؛ صفحهٔ منو/رزرو به ۴۰۴ می‌رفت. فیلتر درخواست اکنون فقط روی URL صفحهٔ معمولی با انتخاب عددی شعبه این برخورد را رفع می‌کند؛ لینک قدیمی و مسیر واقعی صفحهٔ شعبه حفظ شده‌اند.

آزمون صفحات در پنج عرض، WCAG خودکار دسکتاپ/موبایل، ساعت ثبت‌شدهٔ شعبهٔ Fixture، فیلتر و لینک تلفن فارسی و تقویم/ظرفیت واقعی با پاک‌شدن انتخاب قدیمی عبور کرد. فرم رزرو ارسال نشد.

```bash
cd tests/ui
SITE_URL=https://your-disposable-wordpress.example/ UI_STAGE=5 npm test
```
